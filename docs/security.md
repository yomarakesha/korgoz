# Безопасность (Phase 9)

Что защищено, как это устроено и что делать администратору.

## Коротко

- Без входа доступны только `GET /health`, `POST /auth/login`, файлы дашборда `/ui/`
  (страница входа) и Swagger `/docs`. Все остальные эндпоинты отвечают **401**.
- Две роли:
  - **admin** может всё;
  - **user** только читает (GET): дашборд, live view, события, аналитику, людей.
    Любой POST, PATCH или DELETE от него получает **403**.
- Пароли хранятся как хеш **argon2id**. Сам пароль нигде не сохраняется.
- Каждый вход, выход и каждое изменение пишется в **журнал аудита** (`audit_log`).
- После 5 неудачных попыток входа логин и IP блокируются на 5 минут (**429**).

## Первый администратор

Пользователей создаёт админ в дашборде. Первого админа создаёт консольный скрипт: он
работает напрямую с БД.

```bash
source .venv/bin/activate
python -m scripts.create_user admin --role admin      # спросит пароль дважды
```

- Забыли пароль или админ заблокирован:
  `python -m scripts.create_user admin --reset`. Скрипт задаст новый пароль,
  разблокирует пользователя и завершит все его сеансы.
- Для автоматизации пароль можно передать через stdin:
  `echo "$PW" | python -m scripts.create_user bob --password-stdin`.
- `--if-no-users` ничего не делает, если пользователи уже есть. Этот флаг вызывает
  `setup.bat` на Windows.

Требования к паролю: не короче `PASSWORD_MIN_LENGTH` (10) символов и не совпадает с
логином. Логин: 3–64 символа (буквы, цифры, `_ . -`). Регистр в логине не важен:
`Admin` и `admin` — один и тот же пользователь.

## Как устроен вход

1. `POST /auth/login {"username", "password"}` проверяет пароль.
2. Сервер создаёт случайный токен (32 байта) и ставит cookie
   `korgoz_session` с флагами `HttpOnly; SameSite=Strict; Path=/`.
   - `HttpOnly`: JavaScript не может прочитать cookie, поэтому XSS не украдёт сеанс.
   - `SameSite=Strict`: чужой сайт не может отправить запрос с этой cookie (защита от CSRF).
   - Флаг `Secure` включается через `AUTH_COOKIE_SECURE=true`. Включай его, когда API
     работает за HTTPS.
3. В БД (`auth_sessions`) хранится **только SHA-256 токена**. Даже с дампом БД нельзя
   войти под чужим сеансом.
4. Каждый запрос ищет сеанс по хешу и проверяет срок (`AUTH_SESSION_HOURS`, 12 ч) и
   `users.is_active`. Роль читается из БД при каждом запросе, поэтому смена роли
   действует сразу.

### Почему не JWT

ТЗ разрешает «JWT или безопасную session-based auth». Выбраны серверные сеансы по
трём причинам:
- выход, блокировка и сброс пароля **сразу** закрывают сеансы. JWT нельзя отозвать до
  истечения срока без отдельного чёрного списка;
- не нужен секретный ключ подписи, который надо хранить и менять;
- API работает одним процессом, и БД уже есть, поэтому поиск сеанса стоит одного
  индексированного запроса.

### Скрипты и внешние клиенты

Ответ на login содержит тот же токен в поле `access_token`. Его можно передавать
заголовком `Authorization: Bearer <token>`:

```bash
TOKEN=$(curl -s -X POST localhost:8000/auth/login -H 'content-type: application/json' \
  -d '{"username":"admin","password":"..."}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
curl -H "Authorization: Bearer $TOKEN" localhost:8000/cameras
```

Можно и через cookie: `curl -c cookies.txt` при входе, затем `curl -b cookies.txt` в
остальных запросах.

### Live view

`<img src="/cameras/1/stream">` не умеет передавать заголовок `Authorization`, но
браузер сам отправляет cookie. Дашборд и API работают на одном origin, поэтому live view
защищён тем же сеансом. Уже открытый поток не рвётся при выходе. Он закроется, когда
закроется страница.

Внутренний сервер кадров воркера (`LIVE_VIEW_HOST:LIVE_VIEW_PORT`, по умолчанию
`127.0.0.1:8001`) **без авторизации**. Он слушает только localhost, а наружу видео
отдаёт API. Не меняй `LIVE_VIEW_HOST` на `0.0.0.0`.

## Роли и права

| Действие | user | admin |
|---|---|---|
| Дашборд, live view, события, аналитика, треки, люди и их timeline, настройки (чтение) | ✅ | ✅ |
| Сменить свой пароль (`POST /auth/password`) | ✅ | ✅ |
| Камеры и локации: добавить, изменить, удалить | — | ✅ |
| Люди: регистрация по фото, удаление | — | ✅ |
| Пользователи (`/users`), журнал аудита (`/audit`) | — | ✅ |

Правило задано в одном месте: `app/api/auth.py` → `authorize()`. Оно подключается ко
всем роутерам в `app/main.py`: GET/HEAD доступны любому вошедшему, остальное только
admin. Новый POST-эндпоинт на таком роутере автоматически станет admin-only.
`tests/unit/test_auth_api.py` проходит по **всем** маршрутам из OpenAPI и проверяет
401 без входа и 403 для роли user. Если добавить роут и забыть про защиту, тест упадёт.

Админ не может понизить, заблокировать или удалить **сам себя**. Так в системе всегда
остаётся хотя бы один администратор.

Сброс пароля, блокировка пользователя и смена своего пароля завершают сеансы
пользователя. При смене своего пароля текущий сеанс остаётся.

## Защита от подбора пароля

- Если логин не найден, сервер всё равно считает argon2 по фиктивному хешу. По времени
  ответа нельзя узнать, существует ли пользователь.
- Ответ всегда одинаковый: `401 Invalid username or password`. Он не зависит от того,
  неверен пароль, нет такого пользователя или пользователь заблокирован.
- Счётчик неудач ведётся отдельно по логину и по IP (`app/security/login_limiter.py`).
  После `AUTH_MAX_FAILED_LOGINS` (5) неудач за `AUTH_LOCKOUT_SECONDS` (300 с) приходит
  `429` с заголовком `Retry-After`.
- Счётчик хранится в памяти процесса API и сбрасывается при перезапуске. Для одного
  процесса этого достаточно.

## Журнал аудита

Таблица `audit_log`. Смотреть: дашборд → «Журнал аудита» или `GET /audit` (только admin).

| Действие | Когда |
|---|---|
| `LOGIN`, `LOGIN_FAILED`, `LOGOUT` | вход, неудачный вход (с введённым логином), выход |
| `PASSWORD_CHANGED` | пользователь сменил свой пароль |
| `USER_CREATED/UPDATED/DELETED` | админ (или `scripts.create_user`, пользователь `(cli)`) |
| `CAMERA_CREATED/UPDATED/DELETED`, `LOCATION_CREATED/DELETED` | изменения камер и локаций |
| `PERSON_REGISTERED`, `PERSON_DELETED` | регистрация и удаление человека |

- В каждой записи: время, пользователь (id и имя на момент действия), IP, объект и
  подробности.
- В журнал **никогда** не пишутся пароли, адреса камер (там бывает пароль RTSP), имена
  и лица зарегистрированных людей. По людям пишется только id. После удаления человека
  («право на забвение») в журнале не остаётся его данных.
- Запись аудита сохраняется в той же транзакции, что и изменение. Если изменение
  откатилось, записи тоже нет.
- После удаления пользователя его записи остаются: `user_id` становится `NULL`,
  имя сохраняется.
- Чтение данных (просмотр видео, списков) в журнал не пишется.

## Прочее

- Заголовки на всех ответах: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`
  (дашборд нельзя встроить во фрейм), `Referrer-Policy: same-origin`.
- `stream_url` камер API никогда не возвращает, только `stream_url_masked`.
- Секреты (`DATABASE_URL`, `QDRANT_API_KEY`, `CAMERA_URL`) хранятся как `SecretStr`. Логи
  маскируют пароли в URL.

## Если API доступен из сети

1. Поставь перед API reverse proxy с HTTPS (nginx или Caddy), задай
   `AUTH_COOKIE_SECURE=true`.
2. Запускай uvicorn с `--proxy-headers --forwarded-allow-ips=127.0.0.1`. Иначе в
   аудит и в ограничитель попыток попадёт IP прокси, а не клиента.
3. API, воркер, PostgreSQL и Qdrant должны слушать только `127.0.0.1`. Наружу
   открывается только прокси.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AUTH_SESSION_HOURS` | `12` | срок жизни сеанса |
| `AUTH_COOKIE_SECURE` | `false` | cookie только по HTTPS |
| `AUTH_MAX_FAILED_LOGINS` | `5` | неудачных входов до блокировки |
| `AUTH_LOCKOUT_SECONDS` | `300` | окно подсчёта и длительность блокировки |
| `PASSWORD_MIN_LENGTH` | `10` | минимальная длина пароля (не меньше 8) |
