# Замеры производительности (Phase 10)

ТЗ требует не заявлять FPS без замеров. Здесь собраны сквозные замеры всего
конвейера на одной машине и выводы из них: какие настройки брать под 1 и под
несколько камер.

## Как мерили

Скрипт `scripts/benchmark_pipeline.py` собирает тот же конвейер, что и воркер:

```
захват → FrameBuffer → детекция YOLOX → ByteTrack → EventEngine
       (→ распознавание лиц) (→ JPEG для live view)
```

- Каждая «камера» читает `data/samples/vtest.avi` (768×576, 10 FPS) в реальном
  времени, как настоящая камера. Все камеры работают одновременно.
- 5 с прогрева, затем 20 с замера на каждое число камер.
- В базу ничего не пишется. В воркере запись в БД идёт в отдельном потоке
  (`DatabaseWriter`) и не задерживает кадры.
- **Задержка** — время от захвата кадра до момента, когда его обработал последний
  обработчик (трекер, события, распознавание, live view).
- **Потеряно** — кадры, которые обработчик не успел взять: буфер хранит только
  последний кадр, поэтому при перегрузке старые кадры пропускаются, а задержка не копится.
- **CPU** — процент одного ядра: 400% = 4 ядра заняты полностью.

Машина: Lenovo ThinkPad E16 Gen 2, Intel Core Ultra 5 125U (14 логических ядер),
14 ГБ RAM, без GPU. Python 3.12, ONNX Runtime 1.30 (CPU), OpenCV 5.0. Ноутбук от сети.
`DETECTION_INTERVAL=3`: детекция на каждом 3-м кадре, между ними трекер предсказывает
положение.

Live view — один зритель на камеру: каждый кадр рисуется и кодируется в JPEG.
`recognition` добавляет YuNet (лица по всему кадру) на каждом кадре детекции и SFace +
поиск в локальном Qdrant для новых треков. В `vtest.avi` лица мелкие, поэтому SFace
вызывается редко. В кадре с крупными лицами нагрузка будет выше: ~9 мс на лицо
([ai.md](ai.md)).

## Выводы

1. **Задержка p50 около 1 мс у YOLOX-tiny** — это кадры без детекции: на них работает
   только трекер. Задержку p95 задают кадры с детекцией: она примерно равна времени
   детекции. Событие «вход» появляется не позже чем через ~0.15 с после кадра.
2. **`ONNX_NUM_THREADS=0` (auto) расточителен.** Для одной камеры с YOLOX-s он занимает
   ~11 ядер ради выигрыша 40 мс на кадр. Остальные программы на машине будут тормозить.
3. **На этом CPU YOLOX-s тянет 1–2 камеры.** С 4 камерами теряется больше трети кадров.
   Причина — одна модель на все камеры: детекции разных камер конкурируют за ядра.
4. **YOLOX-tiny с 2 потоками тянет 4 камеры без потерь** (~2.5 ядра, ~320 МБ).
   Плата за скорость — хуже находит мелких и далёких людей.
5. **Память растёт на ~40–60 МБ на камеру.** Базовые ~220–280 МБ — модели и библиотеки.
6. Live view почти ничего не стоит при одной камере: JPEG кодируется только
   пока кто-то смотрит live view.

## Рекомендуемые настройки

| Сценарий | Настройки в `.env` |
|---|---|
| 1 камера, максимальная точность | `PERSON_DETECTOR_MODEL_PATH=models/yolox_s.onnx`, `ONNX_NUM_THREADS=4` |
| 2–4 камеры на ноутбучном CPU | `PERSON_DETECTOR_MODEL_PATH=models/yolox_tiny.onnx`, `ONNX_NUM_THREADS=2` |
| Слабый CPU (2–4 ядра) | YOLOX-tiny, `ONNX_NUM_THREADS=2`, `DETECTION_INTERVAL=5`, `CAMERA_MAX_FPS=10` |
| Выделенный сервер, только KörGöz | можно оставить `ONNX_NUM_THREADS=0` (auto) |

Камеры с 25–30 FPS: ставь `CAMERA_MAX_FPS=10–15`. Для подсчёта людей и времени
пребывания больше кадров не нужно, а нагрузка растёт пропорционально FPS.

## Как повторить

Перед замером останови воркер: иначе он делит CPU с бенчмарком.

```bash
python -m scripts.benchmark_pipeline                                      # 1, 2 и 4 камеры
python -m scripts.benchmark_pipeline --model models/yolox_tiny.onnx --threads 2
python -m scripts.benchmark_pipeline --cameras 1,4 --live-view            # + live view
python -m scripts.benchmark_pipeline --recognition                        # + лица (нужен Qdrant)
python -m scripts.benchmark_pipeline --source 0 --cameras 1               # вебка
python -m scripts.benchmark_pipeline --markdown                           # таблица для этого файла
python -m scripts.benchmark_detector --faces                              # только модели, без конвейера
```

Цифры зависят от машины, нагрузки и даже от питания: ноутбучный U-процессор на
батарее сбрасывает частоту. Для своей машины прогоняй скрипт сам и сравнивай
строки между собой, а не с этой таблицей.

## Что не мерили

- GPU: на этой машине его нет. Для CUDA нужен `onnxruntime-gpu` и провайдер в
  `YoloxPersonDetector`.
- Настоящие RTSP-камеры: на захват из сети влияют кодек и сеть. Проверка одной
  камеры — `python -m scripts.check_camera --source rtsp://...`.
- Сутки непрерывной работы (утечки памяти, перегрев). Перед установкой на объект
  стоит оставить воркер на ночь и сравнить RSS в начале и в конце.
